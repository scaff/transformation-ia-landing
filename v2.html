# Hiérarchie d'intention

intention      → ce que vous voulez
   ↓
décisions & conventions → comment vous décidez
   ↓
spec           → ce que la machine doit faire
   ↓
tests          → la limite objective
   ↓
implémentation → ce que l'agent produit

L'agent travaille de bas en haut.
Vous travaillez de haut en bas.
La rencontre se fait sur les tests.
Le geste change

On ne tape plus le code. On donne une intention.

C'est le passage qu'aucune formation IA générique n'enseigne vraiment. L'agent traduit une intention en code. Le métier du développeur monte d'un cran — il devient celui qui formule, qui cadre, qui valide.

Cette montée d'abstraction repose sur une chaîne précise : intention → décisions structurantes → conventions → spec → tests → implémentation. Chaque couche en amont rend la suivante possible. Sans décisions documentées ni conventions, pas de spec lisible. Sans spec, pas de test objectif. Sans test, pas d'implémentation fiable. C'est ce qu'on apprend à pratiquer dans le bon ordre.

Les pratiques d'ingénierie classiques — DDD, hexagonal, TDD, deep modules — retrouvent toute leur valeur. Pas comme dogmes architecturaux. Comme outils de réduction de contexte pour que l'agent fasse bien son travail.

La place des développeurs

Pas un déclassement. Une montée d'un cran.

Cette transformation, qu'est-ce qu'on en pense ? Honnêtement : plus de positif que de négatif. Et c'est ce qu'on veut partager — sans naïveté, sans peur, en regardant les deux côtés.

01

Le métier monte d'un cran.

Coder devenait routinier. Formuler une intention, cadrer un contexte, valider une sortie — c'est plus exigeant, plus créatif, plus proche du sens. Les développeurs y gagnent.

02

Les pratiques d'ingénierie reprennent toute leur valeur.

DDD, hexagonal, TDD, deep modules. Pas comme dogmes — comme outils pour donner à l'agent un contexte qu'il peut traiter. Les seniors qui les maîtrisaient vont voir leur expertise revalorisée.

03

La review devient l'activité différenciante du senior.

L'agent produit. L'humain arbitre. Reviewer du code IA avec une grille — pas à l'intuition — devient la compétence qui change tout. C'est un nouveau métier dans le métier.

04

L'intelligence ne coûte plus rien.

Avant, le coût d'écrire 200 lignes obligeait à avoir une vision claire dès le départ. Maintenant, on peut explorer, jeter, recommencer. C'est un changement de nature de l'activité dev. Pas une accélération — un autre rapport au code.

Ce qu'on évite

Six manières de rater le passage. Six manières de l'éviter.

Le passage à l'IA produit toujours les mêmes accidents. On les a vus chez nos clients, on les a tous traversés. Six grandes catégories — chacune avec sa parade enseignée dans le programme.

01

Intention non captée.

L'agent produit du code plausible qui ne réalise pas ce que vous vouliez.

02

Qualité de codebase.

Surcomplexité, duplication, conventions tacites violées. La codebase se charge en silence.

03

Véracité.

Hallucinations d'API, conseils sécurité confiants et faux, doc qui dérive du code.

04

Confiance déplacée.

Tests qui passent sans rien tester, code « qui a l'air bon » qui passe en review à l'intuition.

05

Opérationnel.

Coût qui explose, fuites de secrets, dépendances vulnérables introduites silencieusement.

06

Humain.

Atrophie senior par fatigue de review, dépendance junior à l'outil, ressenti +20 % / mesuré −20 %.

Le programme

Six modules. Cinq à huit semaines. 70 % de pratique.

Pas de slide deck à présenter à un comité. Du contenu pur, des exercices fil rouge sur des codebases qu'on fournit — un greenfield, un legacy, un projet de production.

Sem. 1

Module 1 — Cadrage & sens

Pourquoi la transition. La place du dev. La hiérarchie d'intention. Mesure baseline, qu'on rejouera à la fin et trois mois après.

Sem. 2

Module 2 — Fondations IA-natives

Prompt engineering vs context engineering. Les trois couches de contexte (tacite, technique, stratégique). Architecture orientée agent. Tests revisités (TDD, mutation, property-based).

Sem. 4

Module 3 — Greenfield

Spec-first vs explore-first. Itérations parallèles autorisées. Quand prototyper, quand cadrer.

Sem. 5

Module 4 — Legacy

Audit de codebase, characterization tests (Feathers), refactor guidé par churn × complexité (Tornhill). C'est là que se joue 80 % du temps des équipes établies.

Sem. 7

Module 5 — Review & qualité

Six modes d'échec, grille de review IA-spécifique, journal d'erreurs détectées. La compétence qui change le métier du senior.

Sem. 8

Module 6 — Production, perf, multi-agent

Observabilité LLM + applicative, méta-observation, garde-fous, multi-agent (et quand ne pas l'utiliser — 80 % des cas un agent unique suffit).

La mesure

Cinq à sept métriques. Avant. Après.

DORA-like (lead time, change failure rate, MTTR), métriques IA-spécifiques (taux d'acceptation, coût par feature, taux de revert post-IA), qualité (bugs en sortie de review, taux de tautologie sur les tests générés). Cinq à sept indicateurs choisis avec vous, pas un tableau de cinquante.

Le ressenti des équipes diverge souvent du mesuré (+20 % perçu, −20 % réel sur certains protocoles d'étude). On vous donne les deux, et on vous apprend à les lire ensemble. Vous présentez le résultat à votre direction, pas une opinion.

Pour qui

Conçu pour les équipes tech. Ouvert au leadership.

Pour vous, si

  • Vous êtes CTO, dirigeant tech, ou tech lead, avec un sponsor côté direction.
  • Votre équipe compte au moins 4 développeurs, à dominante senior.
  • Votre codebase a tests, CI, observabilité minimale (sinon : on commence par auditer).
  • Vous voulez outiller vos développeurs et leur donner leur place dans cette transformation.

Pas pour vous, si

  • Votre équipe est très junior, sans senior pour porter les conventions.
  • Votre codebase est zombie, sans tests ni CI. Il faut commencer par là.
  • Vous voulez « l'IA qui code à votre place ». Ce n'est pas ce qu'on vend, et ce n'est pas ce qui marche.
  • Vous cherchez un slide deck pour un comité. Notre matière, c'est la pratique.

Variante exécutive. Format condensé d'un à deux jours pour CTO et leadership : cadrage, six modes d'échec, mesure, posture. Sans la pratique technique, mais avec les arbitrages structurants. À demander en appel de cadrage.

Pourquoi nous

On code avec l'IA tous les jours. C'est ce qu'on transmet.

La discipline de l'orchestration d'agents sur le code a six mois. Personne ne peut prétendre dix ans d'expérience sur un sujet qui en a six — pas nous, pas eux. Ce qu'on a, c'est la pratique quotidienne sur le code de nos clients. C'est notre métier de delivery au jour le jour.

La méthode qu'on transfère ici est extraite de ce qu'on observe sur le terrain. Choix d'architecture, garde-fous, modes d'échec, mitigations. Pas de la théorie sur slides — du contenu pur.

Il y a plus de positif que de négatif dans cette transformation. C'est ce qu'on veut partager. Pas en niant les pièges — en les nommant pour mieux les éviter.
